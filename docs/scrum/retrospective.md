# レトロスペクティブ（振り返り）

レビューが「成果物」を見る場なのに対し、レトロは「やり方（プロセス）」を点検する場。
KPT（Keep / Problem / Try）形式。

## Sprint 1（交流エピック MVP）

### Keep
- PO判断を明示的に挟めた（分析グラフは落とす／案③／11cまで／バグは検証のみ）
- エピックを 11a〜e に薄切りし、1スプリントぶんに絞れた
- DoD を先に決めた（build/lint/typecheck・ルール過剰開放なし）

### Problem
- 相対見積が外れた：案③は「11b削れば軽い」と見たが、11c(集計)が設計自由度高く実質重め
- 検証が後追い：`firestore.rules` の再デプロイ要・集計コストに実装後のレビューで気づいた
- 一人スクラムの限界：他者の目（デイリー/レビュー）が無く気づきが遅れる

### Try
- 着手前に「デプロイ/運用の影響」を受け入れ条件に1行入れる
- 見積はレンジ（S〜M）で持ち、確定は着手直前のリファインメントで
- ラウンドB（AI-DLC）で「検証を実装の前に置く」型を試し、後追い問題が減るか比較する

## Sprint 2（応援コメント 11b）

### Keep
- 前スプリントのサブコレクション基盤を再利用でき実装が速かった
- 見積（M4）がほぼ当たった

### Problem
- 「11cにコメントも含める？」のスコープ境界判断が都度発生
- ルール再デプロイが依然として手動運用

### Try
- ルール変更を伴うPBIは「再デプロイ手順」をDoDに明記（Sprint1のTryを実践 → 運用ミスを1回防げた）
